## 1. 目标与停止条件

近期唯一要证明的闭环：

> 输入契约与待审材料 → 按需取证 → 使用适用的正式规则 → 有歧义时请求人工裁决 → 交付带证据的审查报告。

本轮定位是停止扩张、验证现有能力，不新增产品机制。冲刺结束时要能拿出五样东西：
- 修复协议说明和纠错反馈后，真实模型新试次的全部结果（含失败）
- 一张先导评测基线表，并与简单基线 B0 并列对比质量、成本和耗时
- 现有项目记忆（冲突、复用、替代、撤回）在真实模型下的分组结果，以及 H03 隔离检查
- 一条外部开发者能复现的 CR02 使用路径
- 用户本人能讲清、能现场修改的实现部分

本轮要回答的核心问题：在少量代表性契约任务上，SpecFlow 相比同模型、同材料的简单审查流程，是否减少了错误、重复澄清或人工整理工作，代价是多少。

**简化结论规则。** 如果 B0 在质量上与 SpecFlow 相当且成本更低，就把“当前任务不需要这部分复杂度”作为正式结论报告，并据此在冲刺后决定保留、简化或停止哪些机制，不再为寻找亮点而增加复杂度。SpecFlow 只在部分用例上胜出时，按用例类型分别报告。

停止条件分两级：
- 阶段 1 出口：F01 在真实模型下至少产出一份报告，即协议通过。这是继续排查的门槛，不是稳定性结论。到 2026-11-10 仍未达到时，阶段 3 只做材料与判据准备，不跑真实批次。
- 冲刺主线出口：至少一份完整报告同时通过冻结判据的协议层、结构断言层和人工语义核对；全部试次及失败结果保留并报告。历史 0/2 与新版本的少量试次只作描述，不声称稳定性显著提升。

### 4.1 阶段 1：协议修复

1. **回放回归。** 归档中的 source_id、observation_id 由宿主运行时生成，新运行不会复现同一组 ID，所以回放分两层：
   - 归档层：从 T01、T02 归档提取冻结输入、源文件、已投影引用、已投影观察和 4 份被拒的真实模型原始响应，作为测试夹具，直接送入现有校验函数。修复前后都必须被拒绝，且拒绝原因与归档一致。
   - 运行层：经真实 runner 与脚本化 adapter，先发出与 T01 同形的非法动作，再发出合法动作。

   验收三项：
   - 原响应仍被拒绝，错误码不变；
   - 纠错反馈的 `issues` 指出字段路径与允许的引用类型；
   - 脚本化的合法后续响应被接受并继续执行。

   固定回放只验证反馈与执行行为；真实模型是否因此改正，由第 6 步的新试次回答。
2. **结构化语义错误。** 新增 `ProtocolViolation(ValueError)`，携带 `path`、出错值和允许的 ID 域。`require()` 与引用校验改抛它；`correction()` 输出与 Pydantic 错误一致的 `issues` 结构。
3. **grammar 字段说明。** 给同名不同域的字段加 `Field(description=...)`，`grammar()` 输出说明。重点是 `reason.evidence_refs`（MaterialRef）、`acceptance_items[].evidence_refs` 和 `findings[].verification_evidence_refs`（外部 evidence_id）。
4. **委派关闭时收窄 grammar。** `delegation=False` 时不暴露 DelegateAction 与 `child_result_reviews`。
5. **guard 参数化。** 时间窗口、单批预算、累计预算改为参数；累计上限 CNY 20。
6. **真实 F01 3 次。** 结果写入阶段报告。

本阶段不改字段名，报告 schema 保持 `v2.1`，只补 T01/T02 实际失败路径需要的反馈，不重写整套校验器。

**接口决策点。** 若 3 次试跑中仍出现引用身份混淆，下一步不再增加提示词或纠错规则，而是提出模型接口简化方案：区分哪些字段必须由模型判断，哪些可以由宿主确定、推导或补全（例如外部核验字段、验收项引用），模型只负责业务结论与证据选择。该方案单独评审，不在本阶段实施。

### 4.2 阶段 2：薄评测入口

不建设通用评测平台，但真实接入不只是加一层循环：
- F01 驱动固定了案例、试次格式和专用 profile；B2 的 `run_case()` 与答题入口经 `require_test_runtime()`（`run_memory_case_prep.py:172`、`:193`、`:314`）限定为离线替身。
- B2 用例是多步编排：发布规则、替代或撤回、多次审查、答题与后继 job。

**入口收口。** 现在 CR02 的启动逻辑散在 `run_f01_pilot.py` 的 `_serve()` 里，`create_app()` 需要外部注入 profile 与 adapter。阶段 2 先提供一个正式的 CR02 启动方式，评测入口和 pilot 都建在它上面：
- 集中加载、校验非敏感配置；集中创建数据库、adapter、Worker；统一启动与关闭顺序，包括 HTTP client 生命周期。
- 真实模型模式必须经过同一套预算、时间窗口和累计预算 guard，有测试证明无法绕过；离线模式使用受控替身，可无 key 演示。
- 不改表结构、不改 `create_app()` 的既有默认行为；连接复用等优化不在本轮。

任务边界：
- 新增一个范围受限的真实评测入口，建在上述正式启动方式上，复用材料准备、`review_evidence.py` 采集和 `diagnose_review.py` 归因。
- 原离线入口及其 `require_test_runtime()` 守卫保持不变，不为复用而放宽。
- 先打通公开单步用例，再打通一个 B2 多步骤用例（建议 R04），通过后再扩展其余用例。

```text
公开 6 例 cases.json + oracles.json；B2 候选（R02–R05、H03）物化后，阶段 2 先打通 R04，其余与 R07 在阶段 3 跑
  → runner：用例 × 试次，进程内 app + 受 guard 约束的真实 adapter
  → 每次运行：review-evidence 归档（复用 review_evidence.py）
  → scorer：协议层 + 结构断言层 + 人工语义层
  → 失败归因：diagnose_review.py
  → results.jsonl（checkout 外）+ 规范化 summary.json / summary.md（入库）
```

| 判分层 | 判定方式 | 指标 |
|---|---|---|
| 协议层 | 自动 | 报告产出率；失败码分布 |
| 结构断言层 | 自动，断言由用户写 | required 命中率、forbidden 违例率、必读源送达率 |
| 语义层 | 人工判定，记录判定人、判据版本、理由 | 无法改写成断言的判据结论 |

**简单基线 B0。** 同一模型、同一批材料、一次调用：把契约、待审材料和（M1 情形下的）正式规则原文直接放进请求，要求输出最简 findings 列表（目标、结论类型、结论、引用原文片段）。不使用 Action 协议、工具、父子 Agent 或账本。
- 范围：公开 6 例，加 R04（附规则原文），每例 3 次。
- 判分：只用两者共有的层次，即 required/forbidden 结论的人工语义核对，以及必读材料是否被引用。SpecFlow 独有的协议层和结构断言层不参与 B0 对比。
- 同表记录调用次数、Token、费用和端到端耗时。
- B0 判分时隐去来源（SpecFlow 或 B0），减少判定偏差。

规则：
- 判据冻结后才跑基线；之后修改判据必须升版本。
- 判据不进入模型请求。
- 全部用例都参与开发，对外称“先导评测”，不声称泛化。
- 不引入 LLM 评委。

### 4.3 阶段 3：现有项目记忆验证

本阶段不改产品代码，只新增评测材料和判据。M0 为 `ruleset_usage.mode = none`；M1 为现有的 `applicable_confirmed` 显式采用。

B2 材料规定取消政策只来自正式规则记录，所以 M0 收不到取消规则时，正确行为是说明缺依据或请求澄清。M0 与 M1 必须按各自输入分别定义正确答案，不能用 M1 的判据给 M0 打分。

**分组预期表**（判据冻结前由用户复核，可细化，不改变分组原则）：

| 用例 | M0 正确行为 | M1 正确行为 |
|---|---|---|
| R02 冲突 | 取消目标缺依据，记缺口或提问 | 指出两条互斥规则并提问，不按发布时间或实现现状裁定 |
| R03 复用 | 取消目标缺依据 | 新 review 采用精确规则版本，按规则检查源码，不重复要求批准 |
| R04 部分替代 | 取消目标缺依据；创建按契约检查 | 创建用旧规则，取消用新规则，报出 queued 取消偏离 |
| R05 部分撤回 | 取消目标缺依据 | 创建仍按规则检查；取消明确缺规则，不推断反向禁止 |

两组共同要求：不编造规则，不越权扩大范围，不建议修改实现，执行状态保持 NOT_RUN。

指标：
- 每组“符合本组预期”的比例，M0 中合理的澄清计为符合，不算失败。
- 记忆收益：M1 相对 M0 增加的、有正式规则依据的明确结论数量。

**H03 单列为隔离检查。** 它验证 A review 的局部答案不进入 B review，不参与 M0/M1 收益对照；可结合 `diagnose_review.py` 的输入隔离检查。

**R07 重叠但兼容（唯一新增材料）。** 两条已确认规则作用于同一 target，且可以同时成立。两条规则涉及的行为都必须在本次 check 范围内，避免把“本次未检查”误判成“漏用规则”。期望结果：两条都被应用，不报冲突。冲突场景由现有 R02 覆盖，不再新增 R06。

多条规则作用于同一 target 时，判据区分兼容（R07）、冲突（R02）、证据不足三种结果，分别统计。

M0/M1 只回答“正式规则进入上下文后，有依据的结论增加了多少”，不用来证明召回或检索能力。

**可选：规则判定纯函数化（用户亲手完成）。** 把 `decisions.py` 中 `adopt()` 的逐 target 判定（生效匹配、版本外、范围不确定、替代切片、撤回切片的原因码计算）抽成不依赖服务对象和数据库连接的纯函数，`adopt()` 只负责读取、调用该函数和组装记录。
- 行为不变：TASK-06 与规则范围相关测试全部通过，且不修改任何断言；为纯函数补直接单元测试。
- 已知影响：CR02 源码指纹改变，旧前缀回放会按既有规则失去复用资格；回放兼容性测试照常通过，不删检查。
- 砍线：阶段 3 的真实批次优先。到 11-16 仍未完成，撤回改动，写入冲刺后路线。

## 5. 验证与流程

- 每次改动后跑定向测试，加 Ruff check 和 format --check；阶段末跑一次全库 pytest。
- TASK-06 决定相关测试与 T01/T02 回放验收必须保持通过。
- 真实批次开跑前说明用例、次数、预估费用和累计费用；guard 硬停。只用 DeepSeek 当前 profile；不读取、不打印凭据。
- 预算单位：一个“试次”是一个用例的完整执行，包括其中全部 review、后继 job 和模型调用（含固定复核），不是一次模型请求。
- 费用估算：T02 共 4 次分析调用，约 CNY 0.079，没有进入固定复核，按它推算完整用例会偏低。规划时按单 review 试次约 CNY 0.2、B2 多步骤试次约 CNY 0.6 粗估：
  - 阶段 1：F01 3 次，约 CNY 0.6。
  - 阶段 2：公开 6 例 × 3 次约 CNY 3.6；B2 先打通 R04 3 次，约 CNY 1.8。
  - 阶段 3：R02–R05 的 M1 各 3 次、M0 各 2 次，H03 3 次，R07 3 次，约 CNY 14.4。R04 的 M1 结果复用阶段 2，可省约 CNY 1.8。
  - B0：7 例 × 3 次，每次一个调用，约 CNY 0.5。
  - 合计约 CNY 19.1，接近 CNY 20 上限。
- 费用检查点：B2 首个试次跑完后，按实际用量重算剩余批次。预计超出上限时，先把 M0 降为每例 1 次，仍不够再请用户决定是否提高上限。
- 每阶段一份短任务单，写明范围、验收、禁止项。阶段末由独立 reviewer 只读审查本阶段 diff 与证据。
- 每阶段一到两个聚焦提交，经用户授权后推到当前分支，不合并 main。
- 结论使用 PASS / FAIL / NOT_RUN；每个数字绑定提交号、profile 和试次数。

## 7. 风险

| 风险 | 应对 |
|---|---|
| 协议修复后真实通过率仍低 | 按失败分类决定是否升级 `v2.2`；数字不好也照实报告 |
| 改 profile 或 schema 触及冻结哈希与迁移 checksum | 本次不改报告 schema；profile 变更使用新的 profile_id |
| 记忆评测被误读为召回能力 | 汇总表注明 M0/M1 只比较正式规则是否进入上下文 |
| 评测入口逐步膨胀成平台 | 只做用例循环、判分和汇总；新需求记入暂缓 |
| 为复用而放宽离线守卫 | 真实入口单独新增，`require_test_runtime()` 原样保留 |
| 费用超出上限 | 按第 5 节费用检查点降级或请用户决定 |
| 协议修复顺势重写整套校验器 | 只补 T01/T02 实际失败路径需要的反馈 |
| 协议仍失败时继续堆提示词 | 按 4.1 接口决策点转向接口简化方案 |
| B0 判分带有对 SpecFlow 的偏向 | 隐去来源后判定，判据先冻结 |
| 时间不足 | 按第 1 节的砍线规则降级阶段 3；规则判定纯函数化按 4.3 砍线 |
| 正式入口让真实调用绕过 guard | 真实模式只能经 guard 创建 adapter，测试覆盖绕过尝试 |
| 纯函数抽取改变记忆行为 | TASK-06 断言不改；抽取前后同一组测试结果一致 |
| 样本过少 | 只称先导评测，保留样本数和适用范围 |
